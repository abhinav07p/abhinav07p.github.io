CurateAI

Multi-Tenant AI News Intelligence Platform

CurateAI ingests about 3,000 technical articles a day from RSS feeds, ArXiv, and HackerNews, collapses duplicates into story clusters, and ranks them against each reader’s persona. Individual readers get a personalized daily newsletter. Enterprise tenants get a strategic research brief shaped by their own company profile. Both run as LangGraph agents orchestrated by Apache Airflow.

Two products on one pipeline

The same ingestion, deduplication, and embedding layer feeds two very different surfaces.

B2C: personalized newsletter

A reader uploads a LinkedIn PDF and an LLM extracts a 10-dimension interest vector. Every like, dislike, or skip nudges a separate behavioral vector. Each morning a writer/editor agent drafts a newsletter from the day’s top clusters, and the reader sends it to their inbox with one click.

B2B: strategic research brief

A company fills in a ten-field profile and an LLM extracts a matching affinity vector. That vector becomes a hard constraint in the generation prompt, so each tenant’s brief (angle, titles, keywords, structure) is visibly different. Keyword velocity from SpaCy NER shows which entities are surging.

System architecture

Snowflake is the system of record, Qdrant holds the embeddings, Airflow runs the nightly pipeline on a GCE VM, and the backend stays a thin trigger layer on Cloud Run.

Ingestion (RSS / ArXiv / HN) → dedup (URL + semantic) → cluster → trend-rank → two parallel LangGraph agents (B2C newsletter, B2B brief) → Gmail SMTP and the Next.js UI. The Claude Desktop MCP surface mounts the same FastAPI service.

Two-layer deduplication

About 3,000 articles a day, many of them syndicated or rewritten. One technique alone is either too expensive or too leaky.

Layer 1: URL dedup

An O(n) hash comparison that catches roughly 80% of duplicates from syndicated feeds, at almost no cost.

Layer 2: semantic dedup

text-embedding-3-small with cosine similarity at a 0.75 threshold catches articles republished under different paths or rewritten by other publishers.

Semantic-only would cost about 4× more. URL-only would let roughly one in five duplicates through. Running both gives the cost profile of the first and the recall of the second.

Personalization engine

Every user persona and every company profile maps onto one shared 10-dimension taxonomy, so retrieval stays unchanged while generation knows each tenant’s vocabulary.

B2C: blended weights

weights[c] = explicit[c] × 0.80 + behavioral[c] × 0.20
weights    = { c: w for c, w in weights if w ≥ 0.05 }

Explicit weights come from onboarding. Behavioral weights drift with every like, dislike, and skip, so tomorrow’s query follows where attention went today.

B2B: affinity as a hard constraint

Early briefs collapsed into boilerplate because every profile field went into one long query. The fix was to extract a 10-dimension affinity vector per company and inject it into the prompt: every title must reference a dominant category, at least three keywords must be phrases a practitioner in that category would search, and zero-weight categories are banned.

LangGraph agents

Both graphs share one base service for retries, cost tracking, and prompt caching, and every node reports latency to one Prometheus histogram.

B2C newsletter (writer / editor)

init→curate→write→editor_review

Loads the persona and blends weights → retrieves and date-scopes articles → drafts the email with a Jinja2 template → second LLM pass as a tone and quality gate. Fast mode skips the editor.

B2B strategic brief (analyst)

intel_extract→brief_build→render_markdown

Scores cross-cluster signals (relevance 40%, velocity 30%, competition gap 30%) → structured Pydantic brief with affinity constraints → Markdown plus persistence. The top article for the date is a mandatory anchor, which keeps a tenant’s briefs distinct day to day.

Key design decisions

Each one was a trade-off with a number behind it.

Airflow on a VM, not Composer

Composer’s floor is about $350 a month for a workload that fits in 8 GB of RAM. An e2-standard-2 VM runs about $48 a month at full utilization, and about $0.12 a day when stopped between demos.

Thin backend, real orchestrator

Pipeline endpoints once ran synchronously, and Cloud Run’s request timeout could kill ingestion mid-MERGE. Moving to Airflow added retries, idempotency, and an audit trail. The API call is now a trigger.

One Qdrant, not two

Dedup and search need identical embeddings in the backend and in Airflow. Qdrant Cloud keeps a single collection so the two sides cannot drift.

Snowflake over Postgres

VARIANT columns store evolving category-weight JSON without ALTER migrations, and the analytical reads (ranking, daily aggregation) suit a columnar engine.

Gmail SMTP over MailerSend

MailerSend’s trial allow-list blocked real recipients. Gmail SMTP with an App Password has no allow-list, enough daily capacity for the demo, and zero marginal cost. Sends are idempotent per user and edition.

Manual send, always

The pipeline generates newsletters but never emails them. Delivery is an explicit user or admin action, never automatic.

Known limitations and next steps

Naming these openly is part of the design.

Security

Auth is stubbed and MCP tools have no request-level authorization. Before any real launch: IAP or Auth0 in front of admin routes and per-user scoping on tools.

Operations

Rate limits are global rather than per user, cost visibility is per model rather than per prompt, and deploys are manual by design until staging environments exist.
